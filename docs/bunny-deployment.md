# bunny.net deployment guide

This guide covers deployment to bunny.net. You can also upload the production
`dist/` build to any other static host.

Use a hostname such as **https://game.example.com** for your deployment.
Replace the example domain and zone names below with your own values.
The provided GitHub Actions workflow waits for successful **Game checks** on
the current `main`, builds it, and uploads only the contents of `dist/` to Bunny
Storage. A dedicated Pull Zone
serves those files through Bunny CDN.

For your own deployment, update the workflow's `environment.url` and summary
URL in [`deploy.yml`](../.github/workflows/deploy.yml), and the featured play link
in [`README.md`](../README.md), to your chosen hostname.

This is a one-time dashboard setup. The repository workflow does not create
zones, change DNS, or manage certificates.

If you don't already use Bunny, you can optionally
[sign up for bunny.net](https://bunny.net?ref=kmaemjuwiy).

## 1. Create the storage and CDN zones

1. In [Bunny's dashboard](https://dash.bunny.net), open **Storage → Add Storage
   Zone**. Use a dedicated zone such as `neon-convoy` (choose an available name)
   and select its primary region.
2. Open the zone's **Access / FTP & API Access** page. Record the exact zone name,
   storage endpoint hostname, and **read/write storage-zone password**.
   For example, Frankfurt uses `storage.bunnycdn.com`, New York uses
   `ny.storage.bunnycdn.com`, and Los Angeles uses `la.storage.bunnycdn.com`.
   The endpoint must match your primary region.
3. Open **CDN → Add Pull Zone**. Create a dedicated game Pull Zone, set its
   **Origin Type to Storage Zone**, and select the zone from step 1.
4. Record its default hostname (for example, `neon-convoy.b-cdn.net`). Names may
   differ from the examples; copy your actual values.

Upload to the storage root: `dist/index.html` becomes `/index.html`, and
`dist/assets/...` becomes `/assets/...`. Do not create a `dist` directory in
storage. The build includes the game's license text and required notice in HTML.
Source, tests, docs, `node_modules`, and the standalone `play.html` are excluded.
Sprites and music are generated by the game; optional Google Fonts need no upload.

Use Bunny's [Vite hosting guide](https://bunny.net/docs/storage/static-site-hosting/vite)
and [Storage HTTP guide](https://bunny.net/docs/storage/http) for the dashboard
flow, regional endpoints, and upload authentication.

## 2. Add the hostname and DNS record

Use your domain's existing DNS provider. If you use Bunny DNS, open
**DNS → your domain** in Bunny's dashboard; otherwise open your provider's DNS
management page.

1. In the game Pull Zone, open **General → Hostnames** and add
   your chosen hostname, for example `game.example.com`.
2. Copy the CNAME target shown there. In the DNS zone for your domain
   (`example.com` in this example), add:

   | Field | Value |
   | --- | --- |
   | Type | `CNAME` |
   | Name / Host | `game` |
   | Target / Value | Your game Pull Zone hostname, e.g. `neon-convoy.b-cdn.net` |
   | TTL | `300` seconds |

   The target is a hostname without `https://` or a path. Use ordinary DNS
   resolution for this CNAME. If using Bunny DNS, leave
   **CDN Acceleration / CDN Proxy disabled** for this record.
   The dedicated Pull Zone already delivers the game through the CDN.
   Enabling acceleration separately creates another Pull Zone and conflicts
   with the hostname mapping. If using Cloudflare DNS, set the record to
   **DNS only**. Preserve the existing apex and other DNS records; you do not
   need to change nameservers to connect this subdomain.
3. After the record propagates, return to the Pull Zone hostname and choose
   **Verify & Activate SSL** (or **Enable → Add Free Let's Encrypt Certificate**).
4. Once HTTPS works, enable **Force SSL** for the game hostname.

The [Custom Hostname guide](https://bunny.net/docs/cdn/custom-hostname) documents
the CNAME flow. See [SSL setup](https://bunny.net/docs/cdn/ssl-setup) for certificate
issuance and [CDN Acceleration](https://bunny.net/docs/cdn/cdn-acceleration) for why
that separate automatic setup is unnecessary here. If your domain has restrictive
CAA records, allow `letsencrypt.org` as described in the SSL guide.

The game has no client-side routes requiring a fallback. Serve `/` as the
storage root's `index.html`; do not turn missing JS/CSS requests into HTML with
a catch-all 404-to-200 rewrite.

## 3. Configure caching

**No Bunny account API key is used.** The runner authenticates only to the
storage zone with its read/write password. It never calls the Pull Zone or
account APIs and does not request cache purges.

Configure the entry page before the first deployment so it stays fresh without
purges. In the dedicated Pull Zone's **Edge Rules**, add one rule with a
**Request URL** condition using **Match Any** for `*://*/` and
`*://*/index.html`. These patterns cover the root and explicit entry page on
all hostnames attached to this game Pull Zone, including query strings.
Add these actions:

| Action | Value |
| --- | --- |
| **Override Cache Time** | `0` seconds (bypass edge caching) |
| **Set Response Header** | Header `Cache-Control`, value `no-cache` |

Save and enable the rule. Keep hashed JS/CSS assets cacheable. Bunny documents
that a zero cache time bypasses content **that is not already cached**: if the
site was served before adding the rule, use the dashboard's **Purge Cache**
button once after saving it. Routine deployments then need no purge.

See [cache-time rules](https://bunny.net/docs/cdn/edge-rules/custom-cache-time),
[URL pattern rules](https://bunny.net/docs/cdn/edge-rules/trigger-path), and
[dashboard cache purges](https://bunny.net/docs/cdn/purge-cache).
The edge rule avoids stale CDN HTML; the response header tells browsers to
revalidate it. Vite's JS/CSS assets use content-hashed filenames, so each new
build gets new asset URLs.

The runner uploads assets before `index.html` and leaves older assets in storage
so cached pages and existing sessions can still load them. It never deletes
remote files. This is an ordered update, not an atomic switch: an interrupted
upload may require rerunning the workflow. Old assets accumulate; if you later
remove them manually, allow for older cached pages first.

## 4. Configure GitHub Actions

In your GitHub repository, open **Settings → Environments → New environment**,
name it
**`bunny-production`**, and restrict deployment branches to **`main`**. For fully
automatic publishing, do not add required reviewers or a wait timer.

Add these **environment variables**:

| Name | Value |
| --- | --- |
| `BUNNY_STORAGE_ZONE` | Exact storage zone name, e.g. `neon-convoy` |
| `BUNNY_STORAGE_HOST` | Regional endpoint hostname, e.g. `ny.storage.bunnycdn.com`; no scheme or slash |

Add this **environment secret**:

| Name | Value |
| --- | --- |
| `BUNNY_STORAGE_PASSWORD` | Read/write **storage-zone password** from its Access page |

Use the storage-zone password, not a Bunny account API key or a Pull Zone token
authentication key. Although Bunny calls the HTTP header `AccessKey`, its value
is the **storage-zone password**, as documented in the
[Storage HTTP authentication guide](https://bunny.net/docs/storage/http).
Keep it in GitHub secrets, never committed files or browser code. The workflow
passes it only to the upload step after installation and checks.
Pull requests and non-`main` manual runs cannot deploy. Forks must configure
their own environment and zones; they do not receive this repository's secrets.

## 5. First deployment and verification

1. After merging the deployment workflow into `main` and finishing the setup,
   open **Actions → Deploy live preview → Run workflow** and select **`main`**.
   This also retries a failed upload after fixing configuration.
2. Check that the main CI gate, installation, build, and uploads succeed.
   The run summary records the actual deployed commit.
3. Visit the default `b-cdn.net` hostname and your custom hostname
   (for example, **https://game.example.com/**).
   Verify the title, deploy a convoy, and confirm the timer advances, drones
   render, and music starts after interaction. Check desktop and mobile controls.
4. In browser developer tools, confirm JS/CSS return successful responses and
   CDN responses show the expected `cdn-pullzone` ID. Check the entry page's
   `Cache-Control: no-cache` header and HTTPS certificate. Request both `/` and
   `/index.html` twice; HTML should bypass the CDN cache rather than return
   `cdn-cache: HIT`. After the next game change, a normal reload should show it.

Optional command-line checks:

```sh
dig +short CNAME game.example.com
curl -I https://game.example.com/
```

Subsequent pushes or merges to `main` deploy when source, entry HTML, favicon,
license, package/build configuration, standalone packaging, uploader, or deploy
workflow changes. Documentation, screenshots, tests alone, and `play.html` alone
do not deploy because they do not change the production site. If adding a new
build input outside the existing path filters, update
[`deploy.yml`](../.github/workflows/deploy.yml) in the same PR.

Deployment runs are serialized and active uploads are not cancelled by new
pushes. A queued or manually retried run builds the latest `main`, so rerunning
an older workflow cannot roll the site back to that run's old game snapshot.
The runner waits up to ten minutes for the checked-out revision's push CI. A
failed, cancelled, or missing CI run prevents upload; rerun failed **Game checks**
first, then retry deployment. Deployment does not reinstall browsers or rerun
the test suite. Require **Game checks** in your `main` branch protection so
changes receive their relevant validation before merging.

For upload HTTP 401 errors, check the storage-zone password and regional host.
For stale content, confirm both HTML cache-rule actions are active; if content
was already cached before enabling the rule, purge it once through the dashboard.
For missing assets, check the storage root and build output; do not upload the
repository or `play.html` as a substitute.
